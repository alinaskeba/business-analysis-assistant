# Business Analysis Assistant

Перший етап — консольний аналіз брифу невеликого вебзастосунку через Gemini API.
Потрібні Python 3.10+ та API-ключ; сторонніх пакетів немає.

## Запуск у PowerShell

```powershell
python .\business_analysis.py --example
```

Перед запуском відкрийте `.env` поруч зі скриптом і заповніть:

```dotenv
GEMINI_API_KEY=ваш-api-ключ
GEMINI_MODEL=gemini-3.1-flash-lite
```

Скрипт автоматично завантажує `.env` незалежно від поточної папки запуску.
Вже задані змінні середовища мають пріоритет над `.env`, навіть якщо вони порожні.
Підтримуються коментарі окремими рядками та значення в одинарних/подвійних лапках;
підстановки змінних і коментарі після значень не підтримуються.
`.env` виключено з Git; `.env.example` — шаблон без секретів.
Після нового клонування скопіюйте `.env.example` у `.env`.
Запуск використовує API-квоту згідно з тарифом облікового запису.

Власний бриф:

```powershell
python .\business_analysis.py --brief "Потрібен застосунок для бронювання кімнат."
python .\business_analysis.py --file .\brief.txt
```

Модель за замовчуванням — `gemini-3.1-flash-lite`; можна задати `--model` або `GEMINI_MODEL`.
Потрібен Gemini API-ключ і доступ до моделі з підтримкою структурованого JSON.
Результат — JSON у stdout, помилки — stderr із кодом завершення 1.

## Схема аналізу v3

Поточний промпт — `brief-analysis-v5-responsibilities`.
[Порівняння з базовим v4](dev/cases/001-meeting-rooms/with-team/roles-v3/review.md):
одночасно змінено схему, промпт і валідатор. Новий живий запуск пройшов Python-валідацію,
але має змістовні пропуски.
[Попередні ітерації](dev/cases/001-meeting-rooms/with-team/prompt-comparison.md) збережено.

- `goals`: ID, опис і `source` з `document: "brief"` та точною `quote`.
- `users`, `team_roles`: один `id` і `name` на роль у категорії, непорожній масив `responsibilities`. Кожен обов'язок має `description` і власний `source`. Одна роль може бути в обох категоріях за наявності джерел.
- `requirements`: ID, опис, джерело та `kind`. Суперечливі формулювання зберігаються окремими вимогами з окремими джерелами.
- `missing_information`: ID, `topic`, `why_needed`.
- `contradictions`: ID, опис, `requirement_ids` щонайменше двох різних вимог.
- `questions`: ID, текст, `target_type: "conflict" | "gap"`, `target_id`, булева `blocks_final_specification`.

Бриф іде у Gemini як текст користувача разом з інструкціями аналітика та схемою.
Ключ передається лише в заголовку `x-goog-api-key`. Вміст `.env` не додається до промпту.
Ролі користувачів продукту не вважаються ролями команди розробки. Якщо команда
не описана, модель має залишити `team_roles` порожнім і додати прогалину та питання.
Ознака блокування — оцінка моделі для перевірки аналітиком, а не автоматичне погодження.
Явна участь у бізнес-процесі зберігається в `users`, навіть коли канал взаємодії
невідомий; для каналу ставиться питання без вигадування інтерфейсу.
Невизначеність, повністю представлена конфліктом, не дублюється як прогалина.
Ці змістовні правила задає промпт; Python не доводить їх семантичне виконання.

## Перший dev-кейс

[Переговорки: бриф і збережені відповіді](dev/cases/001-meeting-rooms/README.md).
Незмінений вигаданий бриф містить конфлікт автоматичного підтвердження та погодження менеджером.
`baseline.*` зберігає першу зафіксовану відповідь старої схеми; `analysis.*` — нову.
Це dev-кейс для розробки, а не незалежний тестовий набір або еталон правильної відповіді.

Повторний запуск (створює нову відповідь у терміналі, не перезаписує збережені результати):

```powershell
python .\business_analysis.py --file .\dev\cases\001-meeting-rooms\brief.txt
python -m unittest -v test_business_analysis
```

## Що перевіряє Python

Перевіряються вхідний текст, ліміт 30 000 символів, наявність ключа, HTTP-помилки,
блокування, завершеність відповіді та JSON. Для аналізу перевіряються:

- точний набір полів, типи, непорожні рядки, enum та справжнє булеве значення;
- формат ID за категорією та їх унікальність; повторення однакового імені ролі в межах категорії (без урахування регістру й крайніх пробілів);
- кожна цитата, включно з усіма вкладеними `responsibilities[*].source.quote`, буквально є у вхідному брифі;
- джерело має позначати вхідний документ `brief`;
- конфлікти посилаються на наявні різні вимоги;
- питання посилаються на наявний елемент правильної категорії;
- для кожного конфлікту й прогалини є принаймні одне питання.

`collect_analysis_errors` повертає список незалежно виявлених помилок із шляхами до полів.
Некоректний батьківський тип пропускає залежні перевірки цієї гілки; інші гілки
продовжують перевірятися. `validate_analysis` піднімає `AnalysisValidationError`
з усім списком `errors`. CLI друкує помилки в stderr, повертає код 1 і не виводить
невалідний аналіз як успішний JSON. Відповідь не виправляється автоматично.
Архівні результати перевіряйте з їхньою збереженою схемою; це не міграція в v3.

Ці перевірки не доводять повноту аналізу, правильність тлумачення цитат або оцінки блокування.
Виявлення всіх суперечностей і збереження обох позицій потребує також змістовної перевірки людиною.
Локальні тести перевіряють прийняття валідного аналізу та відхилення пошкоджених цитат,
ID, посилань, типів і непокритих питаннями прогалин.

Поточний етап зосереджений на аналізі брифу. Вебінтерфейс, генерація документів
і робочий процес затвердження залишаються наступним етапом.

API-формат: [Gemini generateContent](https://ai.google.dev/api/generate-content),
[Structured Outputs](https://ai.google.dev/gemini-api/docs/structured-output).
